Port it to your phone

On this phone, almost everything that is specific to the POCO F6 sits in three places: the device tree generator, the boot shim, and the board drivers in the kernel patches. This page walks through all three and shows where to look up your phone's values.

Before you touch anything, back up your phone. Pull at least persist, modemst1, modemst2, fsg, fsc, boot_a/boot_b, vendor_boot_a/vendor_boot_b, dtbo_a/dtbo_b and vbmeta_a/vbmeta_b. Some of these hold calibration data that is unique to your phone and can't be downloaded anywhere. Keep them out of git.

Check the compatibility page first. This guide assumes a Snapdragon chip with UFS storage and a bootloader that supports fastboot boot.

Step 0: get your phone's hardware map

Everything you need to know about the hardware is already on the phone, in the device tree Android booted with. Boot a recovery with adb (or use a rooted Android) and copy it to the PC:

adb shell cat /sys/firmware/fdt > live.dtb
adb shell cat /proc/iomem > iomem.txt
dtc -I dtb -O dts -o live.dts live.dtb      # dtc is in the device-tree-compiler package

live.dts is a big text file. Every value below comes from searching it. You'll also want your phone's kernel source (Xiaomi, Poco and others publish it on GitHub) for anything the device tree doesn't spell out, like the touch controller's protocol. On this phone the live device tree was read in OrangeFox recovery, because the phone's own Android root was no longer usable.

Also unpack your stock boot.img, because the shim reuses its DTB:

python3 tools/unpack_bootv2.py backup/boot.img dtb/boot_unpacked

1. The device tree generator: tools/mkadt.py

XNU learns about the hardware from an Apple Device Tree. mkadt.py writes one from the constants at the top of the file. These are the ones to change:

ConstantWhat it isWhere to find it in live.dts
PHYS_BASE, MEM_SIZE, and HIGH_PHYS_BASE, HIGH_MEM_SIZEThe RAM the kernel may useThe memory node, plus every entry under reserved-memory. Pick a range with no carve-outs in it. The high-memory window is the top DDR bank; on this phone it is 0x08c0000000 / 0x0c0000000, 3 GiB contiguous.
GICD, GICRInterrupt controllerinterrupt-controller@... with compatible = "arm,gic-v3". The first two reg entries: 0x17100000 and 0x17180000 here, with GICR_SIZE 0x200000 and a PE stride of 0x40000.
FB, FB_SIZEThe screen buffer the bootloader leaves oncont_splash_region (sometimes splash_region) under reserved-memory. On this phone the buffer is at 0xe3940000.
FB_W, FB_H, FB_STRIDEPanel resolution and bytes per lineThe panel node (qcom,mdss_dsi_...), qcom,mdss-dsi-panel-width and -height: 1220 and 2712 here. Stride is width x 4, so 4880.
UFS, UFS_SIZEThe storage controllerufshc@..., the reg named ufs_mem: 0x1d84000 here, size 0x3000.
TIMEBASE, VTIMER_INTID, PTIMER_INTIDSystem timerThe timer node with arm,armv8-timer. The frequency is almost always 19.2 MHz on Snapdragon. The virtual timer is a PPI number n and becomes INTID 16 + n: 27 for the virtual timer and 30 for the physical timer on this phone.
CPU nodesHow many cores, and their hardware IDsThe cpus node: each core's reg (its MPIDR). This phone has 8 cores, 3 in the first cluster, 4 in the second and the X4 prime in the third; the loop in mkadt.py builds them as core << 8.

2. The boot shim: shim/

The shim is the small program the bootloader starts. It has its own copy of a few addresses, because it runs before any device tree is read:

  • shim/console.h and shim/mmu.h: the framebuffer address (FB_BASE, FB_PHYS) and the panel size (FB_W 1220, FB_H 2712, stride FB_W * 4).
  • shim/shim.c: GICD_BASE, GICR_BASE, GICR_SIZE, GICR_PE_SIZE, the timer interrupts (VTIMER_INTID 27, PTIMER_INTID 30), IMEM_RESTART_REASON and PSHOLD. On this phone the reset itself goes through PSCI_SYSTEM_RESET, and the restart reason is a scratch word at 0xa9000000 inside the RAM window.
  • shim/build.sh: the mkbootimg offsets and header version. Copy them from your stock boot.img: the unpack script prints its header with the load addresses and page size.

Two kernel patches also draw on the screen very early, before the device tree is parsed: 0010-sweet-early-framebuffer-debug and 0012-sweet-keep-debug-console-after-ttbr0. They hard-code the framebuffer address and the panel size. Change those too, or the early boot messages will land in the wrong place.

3. The board drivers: xnu/patches/

The kernel is Apple's source plus a numbered series of patches that GitHub Actions applies in order. Most patches are generic. These are the ones that know about the board:

PatchWhat to check
0091-peridot-logical-display-and-peripheral-guardDisplay: the kernel presents the iPhone X logical canvas (1125 x 2436) instead of the panel's native size, with signed centering offsets for the larger physical panel. It also adds the guard that refuses the SM7150 key, touch and USB probes on SM8635, because those registers mean something else here.
0092-sweet-save-first-panic-to-ufsStorage and diagnostics: the persistent console log, the first panic saved to UFS, and the optional sweetpanicreset / sweetdiagreset behaviour.
0095-sweet-spmi-peridot-probe and 0097-peridot-spmi-v7-keysButtons: the SPMI arbiter. This board uses the v7 arbiter, so the read command encoding and the address encoding differ from the older one. The key registers are the PMK8550 power/resin lines and a PMXR2230 GPIO, and the driver delivers them as HID consumer keys. The earlier sweet addresses must not be used.
0098-peridot-geni-spi-goodix-probeTouch: the serial engine. SE4 at 0xa90000, the qcom,cliffs-gcc clock votes, the TLMM pin muxing for the four panel pins, and the Goodix BerlinD read protocol (F1 plus a big-endian address, three dummy bytes, then the data, with a checksum on the block).
0101, 0102, 0103, 0104 (GPI DMA)Touch, second attempt: the GPI DMA transport over the same engine. A private, page-aligned arena holds the TX/RX rings and the event ring, the SMMU routes the DMA to it, and 0104 adds the bounded event trace and the timeout diagnostics. The transfer itself works; the completion event does not arrive yet.
0108-peridot-bitbang-spi-and-touch-powerTouch, the simple path: the four panel pins are muxed back to plain GPIOs and driven by hand, which needs no DMA engine and no SMMU. The same patch votes the panel's rails (AVDD and IOVDD through RPMh) and sequences the reset on the panel's GPIO.

The patches add new files to XNU, such as bsd/dev/sweet_ufs.c and bsd/dev/sweet_spi_peridot.c. To change one, apply the series to an xnu-8796 tree, edit the file, and regenerate that patch with diff -u. Before you spend a CI run, tools/xnu-cc.py can compile a single file locally using the commands from a previous CI log.

4. Boot arguments

The command line is baked into the payload by tools/mkpayload.py (see the README for the full line). The ones that matter on this phone:

ArgumentWhat it does
sweetdiagreset=NCapture and reset after N seconds (30 to 3600). This is the timer that bounds a session and puts the machine back into the bootloader.
sweetfb_noconsole=1Pause the kernel text console once the display is up, so the UI is not covered in boot messages.
sweetfb_native=1Present the panel's native size instead of the iPhone X logical canvas.
sweetfbshot=NTake a read-only framebuffer snapshot after N seconds and write it into the console log, so the screen can be pulled out as a PNG.
peridotspi=NSelect the touch diagnostic stage: 1 is the native serial-engine probe, 4 the GPI DMA diagnostics, 6 the bit-banged SPI transport.
sweetkeys=0, sweettouch=0, sweetusb=0Disable one driver, so the rest can be tested in isolation.
cpus=NHow many cores to bring up. Start with 1 and raise it once the kernel is stable.

5. Build and boot

The kernel is built by GitHub Actions, and the payload is the kernel plus the device tree plus the boot arguments:

python3 tools/mkpayload.py xnu/out-0107/kernel.development.sweet \
    shim/out/peridot-0092-mac.adt shim/out/payload.bin --cmdline '...'
bash shim/build.sh out/payload.bin

tools/peridot-cycle.py IMAGE OUT then runs a whole session unattended: it backs up the boot control block, reboots into fastboot, boots the image temporarily, waits for the kernel to reset itself and pulls the console log back. Nothing is flashed, so the Android installation is still there afterwards; the iOS root volume in userdata is the exception, and it replaces Android's user data.

Take it in stages. You can test the shim and kernel before anything is written: boot the shim alone, and it prints its own diagnostics to the screen.

  1. Shim text on screen. Your framebuffer address is right.
  2. Kernel messages scroll. Memory, interrupts and the timer are right. If the phone reboots instantly, the memory range probably overlaps a protected carve-out.
  3. The UFS driver finds the disk. Then iOS starts from userdata. This is the point where the iOS root volume has to be in place.
  4. Apple logo, then the lock screen. The logical canvas has to be right, otherwise the display code loops instead of presenting frames.
  5. Keys and touch come last. They arrive as HID events, and a key that reaches a live HID client is already a good sign.

When something crashes, the console log is on the device and tools/peridot-cycle.py pulls it; tools/sweet-crash.py symbolizes crash reports from the console log. NOTES.md has every problem the peridot port ran into along the way, and most of them will show up on your phone too.

Got further on your phone? Post it on r/hackios. Which chip, which step you reached, and what you had to change helps everyone after you.
